# ADR 0003: Decouple Templates and Overlay from the Generator Engine

**Status:** Executed (2026-09-03)

> **2026-09-03 update:** All steps of the migration path have been carried out.
> `templates/` and `overlay/` were copied to the target `google.cloud` collection
> repository beforehand; this repo's `overlay/` directory has been removed entirely,
> and `templates/` has been replaced with the generic FIXME skeleton described below.
> `main.go` embeds the skeleton `templates/` tree via `//go:embed all:templates`,
> `pkg/renderer` accepts an `fs.FS` instead of a disk path, and template resolution
> follows the explicit/default/embedded-fallback logic specified below. Collection
> authors are expected to point `--templates`/`--overlay` at their own copies (e.g.
> the collection repo checked out alongside this one) for day-to-day development;
> running with no `templates/`/`overlay/` present produces structurally valid but
> non-functional (`FIXME`-marked) output, by design.

## Motivation

`ansible-mmv1` is designed to be a general-purpose code generator that reads Google
Cloud resource definitions from Magic Modules (MMv1) YAML files and produces Ansible
collection modules. However, the `templates/` and `overlay/` directories currently
live inside this repository, and they are tightly coupled to a single consumer: the
`google.cloud` Ansible collection.

The templates contain:
- Google-specific copyright and license headers (GPL v3, `Copyright (C) Google`)
- Hardcoded `ansible_collections.google.cloud.plugins.module_utils` import paths
- Google-branded example variables (`gcp_project`, `gcp_cred_kind`, `gcp_cred_file`)
- Google-branded test aliases (`cloud/gcp`, `cloud/gcp/v2`)
- Google-branded metadata (`supported_by: community`)

The overlay directory contains resource-specific YAML overrides and Ansible sample
templates that are only relevant to the `google.cloud` collection.

This coupling prevents the tool from being used as a standalone engine that other
collections could adopt. It also prevents a key workflow: running the generator from
the target collection's directory via `go run github.com/thekad/ansible-mmv1@latest`,
because the templates directory is not available on disk when Go downloads and builds
the binary.

## Decision

Move both `templates/` and `overlay/` out of this repository and into the target
collection repository. Replace the current templates with a minimal skeleton that
serves as documentation and a starting point for new adopters.

### What stays in this repository

1. **The Go engine** - all code under `pkg/`, `main.go`, `go.mod`, etc.
2. **Skeleton templates** - a minimal, functional `templates/` directory that produces
   valid (but generic) Ansible modules. These serve as:
   - A reference implementation showing the template contract (which `{{ define }}`
     blocks are required, which Go struct fields are available)
   - A quickstart for new collection authors
   - A fallback so that `go run ...@latest` produces *something* rather than failing
3. **Configuration and docs** - `mmv1-config.yaml`, ADRs, README, etc.

### What moves to the collection repository

1. **Production templates** - the full `templates/` directory with all Google-specific
   branding, imports, and behavior
2. **Overlay directory** - all `overlay/products/`, `overlay/info/`, and
   `overlay/templates/ansible/samples/` content

### Skeleton template design

The skeleton templates must produce structurally valid Python modules that demonstrate
the full template contract. They are generic - no collection-specific branding - and
clearly marked with `FIXME` comments indicating where customization is expected.

#### `templates/base/fragments.tmpl`

Defines the required `{{ define }}` blocks: `autogen_notice`, `license_notice`,
`python_file_header`, and `info_module_examples`.

```
{{- define "autogen_notice" -}}
# ----------------------------------------------------------------------------
#
#     ***     AUTO GENERATED CODE    ***    Type: MMv1     ***
#
# ----------------------------------------------------------------------------
#
#     This file is automatically generated by ansible-mmv1 and manual
#     changes will be clobbered when the file is regenerated.
#
# ----------------------------------------------------------------------------
{{- end -}}

{{- define "license_notice" -}}
# FIXME: Replace this with your project's license header
{{- end -}}

{{- define "python_file_header" -}}
#!/usr/bin/python
# -*- coding: utf-8 -*-
#
{{ template "license_notice" . }}
{{ template "autogen_notice" . }}
#
{{ end -}}

{{- define "info_module_examples" -}}
# FIXME: Replace the collection name below with your own (e.g. my_namespace.my_collection)
- name: List all {{ $.Name }} resources
  FIXME.COLLECTION.{{ $.Name }}:
    project: "{{ "{{" }} project {{ "}}" }}"
  register: result

- name: List {{ $.Name }} resources matching given filters
  FIXME.COLLECTION.{{ $.Name }}:
    filters:
      - display_name = "my-resource"
    project: "{{ "{{" }} project {{ "}}" }}"
  register: result
{{- end -}}
```

#### `templates/plugins/module.tmpl`

The skeleton module template is a **complete copy** of the current production
`module.tmpl` with only the following branding lines replaced:

| Current (Google-specific) | Skeleton replacement |
|---|---|
| `from ansible_collections.google.cloud.plugins.module_utils import gcp_v2` | `import FIXME_module_utils as module_utils  # FIXME: replace with your collection's module_utils import` |
| All references to `gcp_v2.` in the template body | `module_utils.` |
| `"supported_by": "community"` | `"supported_by": "FIXME"` |

Everything else remains **identical** to the production template. The skeleton
produces a Python file with:
- Complete `DOCUMENTATION` block (generated from `$.Documentation.ToString`)
- Complete `EXAMPLES` block (from `$.Examples.ToString "doc"` - empty if no overlay)
- Complete `RETURN` block (from `$.Returns.ToString`)
- Full `argument_spec` (from `$.ArgumentSpec.ToString`)
- All nested resource classes with `_request()` / `_response()` methods
- Encoder / decoder hooks (from `$.CustomCode.Encoder` / `$.CustomCode.Decoder`)
- All custom_code hook points (`PreRead`, `PostRead`, `PreCreate`, `PostCreate`,
  `PreUpdate`, `PostUpdate`, `PreDelete`, `PostDelete`, `CustomCreate`,
  `CustomUpdate`, `CustomDelete`, `PostCreateFailure`)
- Complete CRUD dispatch in `main()` with async LRO support
- Scopes, operation configs, resource refs - all driven by Go struct fields

The resulting Python file will fail at **import time** (not generation time) due to
the `FIXME_module_utils` import, making it immediately obvious what needs replacing.

#### `templates/plugins/module_info.tmpl`

Same approach as `module.tmpl`. Complete copy with only the import line and
`module_utils` references replaced:

| Current (Google-specific) | Skeleton replacement |
|---|---|
| `from ansible_collections.google.cloud.plugins.module_utils import gcp_v2` | `import FIXME_module_utils as module_utils  # FIXME: replace with your collection's module_utils import` |
| All references to `gcp_v2.` | `module_utils.` |
| `"supported_by": "community"` | `"supported_by": "FIXME"` |

The info module template is simpler (no CRUD dispatch) but still exercises the full
info module contract: `$.DocumentationInfo.ToString`, `$.ArgumentInfoSpec.ToString`,
`$.ReturnInfo.ToString`, `$.Scopes`, `$.BaseUrl`, `$.OperationConfigs`,
`$.CollectionKey`, custom_code hooks (`PreRead`, `PostRead`, `CustomImport`).

### Embedding the skeleton templates via `go:embed`

The skeleton templates are embedded into the compiled binary using Go's `embed`
package. This is the mechanism that makes `go run github.com/thekad/ansible-mmv1@latest`
work without requiring the template files to exist on disk.

In `main.go`, add after the existing imports:

```go
import "embed"

//go:embed templates/*
var embeddedTemplates embed.FS
```

**Important:** Go's `//go:embed` does not match files in subdirectories with a simple
`templates/*` glob - it requires `all:templates` or explicit subdirectory patterns.
Use `//go:embed all:templates` to recursively include all files under `templates/`.

The `embed.FS` includes the directory prefix (`templates/base/fragments.tmpl`), so
`fs.Sub(embeddedTemplates, "templates")` is used to strip it, making internal paths
(`base/fragments.tmpl`, `plugins/module.tmpl`) identical whether they come from the
embedded FS or from a disk directory via `os.DirFS()`.

### Refactoring `pkg/renderer` to accept `fs.FS`

The renderer currently uses filesystem paths (`TemplateDirectory string`) and reads
templates via `tmpl.ParseFiles()`. This must change to accept an `fs.FS` so it can
work with either a real directory or an embedded filesystem.

#### Changes to `pkg/renderer/renderer.go`

**1. Replace `TemplateDirectory` with `templateFS` in the struct:**

```go
// Before:
type TemplateData struct {
    TemplateDirectory        string
    OutputFolder             string
    ModuleDirectory          string
    IntegrationTestDirectory string
    OverWrite                bool
}

// After:
type TemplateData struct {
    templateFS               fs.FS   // unexported - internal use only
    OutputFolder             string
    ModuleDirectory          string
    IntegrationTestDirectory string
    OverWrite                bool
}
```

**2. Change `NewTemplateData` signature:**

```go
// Before:
func NewTemplateData(templateDirectory, outputFolder string, overWrite bool) *TemplateData

// After:
func NewTemplateData(templateFS fs.FS, outputFolder string, overWrite bool) *TemplateData
```

Remove the `filepath.Abs(templateDirectory)` call (no longer needed - the FS is
already rooted). Keep the `filepath.Abs(outputFolder)` call (output is always a disk
path).

**3. Change `executeTemplate` to use `ParseFS` instead of `ParseFiles`:**

```go
// Before:
templatePath := path.Join(td.TemplateDirectory, templateName)
tpls := []string{
    path.Join(td.TemplateDirectory, "base", "fragments.tmpl"),
    templatePath,
}
// ...
funcs := funcMap(os.DirFS(td.TemplateDirectory))
// ...
tmpl, err := tmpl.ParseFiles(tpls...)

// After:
tpls := []string{
    "base/fragments.tmpl",
    templateName,
}
// ...
funcs := funcMap(td.templateFS)
// ...
tmpl, err := tmpl.ParseFS(td.templateFS, tpls...)
```

Key differences:
- Template paths are now **relative to the FS root** (e.g. `"plugins/module.tmpl"`)
  instead of absolute filesystem paths
- `os.DirFS(td.TemplateDirectory)` becomes `td.templateFS` (already an `fs.FS`)
- `tmpl.ParseFiles(tpls...)` becomes `tmpl.ParseFS(td.templateFS, tpls...)`

**4. No changes to `pkg/renderer/utils.go`:**

The `funcMap(templateFs fs.FS)` function already accepts `fs.FS` - no change needed.
It passes the FS to `google.TemplateFunctions(templateFs)` which uses `ParseFS`
internally for `trimTemplate` and `customTemplate`.

### Changes to `main.go` - template resolution

Replace the current `filepath.Abs()` logic in `runGenerate()` with FS resolution:

```go
// Before (current code around line 470):
ansibleTemplateDir, err := filepath.Abs(viper.GetString("templates"))
if err != nil {
    log.Fatal().Err(err).Msg("invalid ansible templates path")
}
// ...
templateData := renderer.NewTemplateData(ansibleTemplateDir, output, overwrite)

// After:
var templateFS fs.FS
templatesPath := viper.GetString("templates")
if cmd.Flags().Changed("templates") || viper.IsSet("templates") {
    // User explicitly set --templates or templates: in config file.
    // The path MUST exist - fatal error if it doesn't.
    absDir, err := filepath.Abs(templatesPath)
    if err != nil {
        log.Fatal().Err(err).Msg("invalid templates path")
    }
    if _, err := os.Stat(absDir); err != nil {
        log.Fatal().Err(err).Msgf("templates directory does not exist: %s", absDir)
    }
    templateFS = os.DirFS(absDir)
    log.Info().Msgf("using templates from: %s", absDir)
} else {
    // Default "templates" value - check if it exists on disk, fall back to embedded.
    absDir, _ := filepath.Abs(templatesPath)
    if _, err := os.Stat(absDir); err == nil {
        templateFS = os.DirFS(absDir)
        log.Info().Msgf("using templates from: %s", absDir)
    } else {
        sub, err := fs.Sub(embeddedTemplates, "templates")
        if err != nil {
            log.Fatal().Err(err).Msg("failed to load embedded templates")
        }
        templateFS = sub
        log.Warn().Msg("no custom templates directory found, using built-in skeleton templates")
    }
}
templateData := renderer.NewTemplateData(templateFS, output, overwrite)
```

The distinction matters:
- **User explicitly set `--templates` or config file `templates:` key** - the path
  must exist. Fatal error if it doesn't. This prevents silent fallback to skeleton
  when a user has a typo in their path.
- **Default value `"templates"` with no explicit override** - check if a `templates/`
  directory exists in the current working directory. If yes, use it. If no, fall back
  to the embedded skeleton and log a warning.

The `--templates` / `-T` flag and `templates` viper key are already bound via
`mustBindPFlag("templates", "templates")` (added in a prior commit). The flag default
remains `"templates"`.

### Overlay behavior

The `--overlay` / `-O` flag already defaults to `"overlay"`. No change needed:
- If the directory exists in cwd, it is used
- If it does not exist, no overlay is applied (upstream MMv1 YAML only)
- A warning is logged when no overlay directory is found

## Consequences

### Positive

- `ansible-mmv1` becomes a reusable engine that any collection can adopt
- `go run github.com/thekad/ansible-mmv1@latest` works from any collection directory
- Clear separation of concerns: engine vs. collection-specific content
- The skeleton templates serve as living documentation of the template contract

### Negative

- The `google.cloud` collection repository grows by the templates and overlay content
- Developers working on the engine need the collection repo checked out alongside
  to do end-to-end testing (or use `--templates` / `--overlay` to point at it)
- The skeleton templates produce modules with `FIXME` markers that won't work without
  customization - this is intentional and made visible by the runtime warning

### Migration path

1. Copy `templates/` and `overlay/` to the target collection repository
2. Replace the current `templates/` in this repo with the skeleton versions
   (as specified in the skeleton template design section above)
3. Add `//go:embed all:templates` and `var embeddedTemplates embed.FS` to `main.go`
4. Refactor `pkg/renderer/renderer.go`:
   - Change `TemplateData.TemplateDirectory string` to `templateFS fs.FS`
   - Change `NewTemplateData` signature to accept `fs.FS` instead of `string`
   - Change `executeTemplate` to use `tmpl.ParseFS()` instead of `tmpl.ParseFiles()`
   - Change `funcMap` call from `funcMap(os.DirFS(...))` to `funcMap(td.templateFS)`
5. Update `main.go` `runGenerate()`: replace `filepath.Abs()` template resolution
   with the FS resolution logic (explicit path vs default vs embedded fallback)
6. Update `mmv1-config.yaml` and docs to reflect the new workflow
7. Update AGENTS.md to describe both the engine repo and the collection repo workflows
